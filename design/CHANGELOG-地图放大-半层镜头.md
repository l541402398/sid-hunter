# CHANGELOG：地图 2× 放大 · 半层镜头（方案 B）· 每层 6 间房

日期：2026-10-17 晚（跨 18 日凌晨）
分支：`feature_dev_floor`（工作树，基于 `1232e8f`）

## 背景

上一轮把每层扩到 1440×400、加了 14 间独立房间后，用户反馈：

1. 「每一层还是太小了，主空间太小，独立空间太少。到时候游戏会容纳最多五六百人同时在线。」
2. 「放大倍数你考虑。网络这个情况，每个用户只加载他当前控制人物同层的人物如何？」
3. 「放大了，要在主空间和独立空间添加物品素材。」
4. 视野 A/B 决策：选 **B** ——「镜头拉远到 1440×960，一屏看半层，人显得小一点」。

## 一、尺度：2×，且服务端/浏览器同源

- `online/shared/world/config.js`：`FLOOR_SCALE` 默认 **2**（Node 可用 `SID_FLOOR_SCALE` 覆盖做对照）。
  - 楼层 `1440×400 → 2880×800`（4 倍面积）
  - 速度 `144 → 288 px/s`
  - 逻辑视野 `VIEW_W = 720*scale = 1440`、`VIEW_H = 400*scale = 800`（服务端裁剪用）
- `floors.js` / `rooms.js` 不再各自读环境变量，统一读 `config.js` 的 `FLOOR_SCALE`。
- **浏览器注入**：`server/http-util.js` 在托管 `/shared/world/config.js` 时，于响应体前写入
  `window.__SID_FLOOR_SCALE__ = <服务端值>;`。浏览器无法读 env，这一步保证两端永远同比例；
  否则会出现「服务端按 2880 判碰撞、客户端按 1440 画图」的错位。

## 二、镜头：方案 B

- 楼层视野宽固定 `FLOOR_W / 2`（2× 时 **1440 世界像素**），高度按地图视区比例自适应
  （3:2 时即 **1440×960**）。`game.js` 的 `applyViewport()` 统一计算。
- 高度上限 `FLOOR_H * 1.5`，避免竖屏把视野拉到楼外。
- 进入房间：镜头切换为**整间屋子 contain 铺满视区**（620×420 的房间在 965×635 视区里放大 ~1.5×），
  出房恢复半层视野。解决放大后「房间比镜头还小、四周露出楼层草地」的观感问题。
- 房间尺寸**不随楼层放大**：房间是"另一间屋子"，不是大厅；否则 620×420 → 1240×840 会空得离谱。

  - 4F 森林：林间小屋、守林人哨站、猎人营地、草药棚、树屋、瞭望塔
  - 5F 地牢：宝库、献祭祭坛、刑讯室、墓室、炼金地窖、囚室
  - 6F 海盗：船长室、货舱、厨房、弹药库、水手舱、瞭望室
  - 7F 赛博：顶层公寓、霓虹后巷、义体诊所、数据黑市、酒吧、天台花园
- **门点 bug 修复**：原先 `spec.door` 是 1× 世界像素，`FLOOR_SCALE=2` 后房间门全挤在原西侧，

  `online/room-door-scan.mjs` 按「可站立 + 从出生点 BFS 可达 + 门间距 ≥160px」挑选。

### 7.2 `clutter.js`：按楼层世界观撒陈设

- 数据在 `dressing.js` 的 `THEME_CLUTTER`：每层 5–8 种素材 + 权重 + 绘制尺寸；
  逻辑在 `clutter.js`：确定性网格（固定种子）+ 3 轮抖动，逐点检查：
  - 基座在楼面内、`y >= 350`（不压主走廊）、不超南边界；
  - 基座 22px 不与既有家具/墙重叠（树冠可叠在桌后，保持景深）；
  - 与房间门牌 ≥110px、电梯厅视觉矩形 +70、出生点 ≥60；
  - 每层上限 88 件，实际落到 **49–65 件**（空地多少决定）。
- 每件陈设 = 普通 `floor.furniture` 项，`f.prop` 指定素材，`f.blocks` 只有基座 16px：
  行走可绕、渲染走既有深度排序，不引入第二套渲染路径。
- 独立房间同样处理：42 间房各补 ≤7 件小件（避开入口/出口/门洞），共 **281 件**。
- 客户端 `scene.js` 的 `themeSpec()` 支持单件 `f.prop` 覆盖，因此新素材不需要往
  `THEME_FURN` 里塞假 type。
